# Architecture

Hot Potato begins as one deployable system with explicit package boundaries. It is not a collection of networked microservices.

## Request path

1. `POST /api/route` validates a lead payload and optional external ID.
2. When HubSpot is connected, the server discards any caller-supplied owner, looks up the contact by email, and resolves its active owner before routing. A missing contact or unassigned owner is a normal unowned lead; missing scope, provider failure, or an unverifiable response fails closed under a bounded deadline.
3. The repository loads active rules, pools, representatives, schedules, assignment state, and eligible route candidates.
4. When reps connect Google or Outlook individually, the API checks each candidate through that rep's selected named calendars and encrypted provider tokens. It holds disconnected, stale, or unverifiable reps out of the route. If no rep-level connection exists, the organization-level Google/Microsoft connection remains the fallback.
5. The pure router evaluates conditional rules by priority, then one condition-free catch-all if present. It filters eligible reps, preserves an authoritative current owner when eligible, or selects the least-served weighted rep.
6. A pool-scoped PostgreSQL advisory lock serializes assignment state changes.
7. The decision, availability source, new assignment count, and CRM writeback job commit together.
8. The worker claims the job with `FOR UPDATE SKIP LOCKED`, refreshes OAuth tokens when needed, and invokes HubSpot or the development adapter.
9. `POST /api/bookings` treats the caller's external ID only as source idempotency. The server mints a separate random management capability and provider transaction, rechecks the exact quoted conflict-calendar/account snapshot, then queues `calendar.event.create`. The worker writes through the booking-bound provider account rather than whichever account happens to be connected later.

## Public scheduling path

1. `/schedule/{organization}/{meeting-type}` resolves an active meeting type targeting one rep or one pool without exposing rep email or OAuth state.
2. The pure scheduling domain expands each eligible organizer, required fixed co-host, and required co-host-pool candidate's effective weekly hours, replacing a weekday with its date-specific override when present; an empty override blocks that date. An effective week is either custom or the transactionally mirrored value of a workspace reusable schedule, so hot routing reads never need a second availability engine. The web process unions busy intervals from every named Google and Outlook calendar each participant selected, removes those intervals and any local day or Monday–Sunday week already at that participant's meeting limit, intersects each organizer with every fixed requirement and at least one person per required pool, then unions the remaining organizer availability. One organizer-selected provider receives the event and conferencing link on Google primary or Outlook default. Selected calendars that disappear fail that participant closed until refreshed or deselected.
3. The browser renders slots in the recipient's timezone while preserving exact UTC timestamps for booking.
4. `POST /api/scheduling/bookings` re-fetches live availability, accepts only an exact currently offered slot, and selects one eligible pool organizer with weighted round robin. It locks the normalized invitee email or exact-domain allowance when configured, then every organizer, co-host pool, and quoted participant in stable order; revalidates each calendar identity, configuration snapshot, overlap, meeting limit, and buyer allowance; then fairly selects a distinct person for every pooled role and snapshots the meeting team. A newly unavailable organizer or pooled co-host is skipped while another valid combination can still honor the slot.
5. A durable booking row, booking-snapshotted co-host rows with source-pool labels, snapshotted reschedule/cancellation deadlines, one unified participant-reservation ledger, PostgreSQL range exclusion, and capacity trigger prevent concurrent overlap or excess local daily/weekly load across organizer and required co-host roles. Required pooled selections reserve time and advance their pool's assignment state; optional selections advance fairness and receive invitations without reserving time. Cancelled meetings release every reservation and their buyer allowance. Pending and provider-uncertain meetings retain them; a pending reschedule counts once per local period while protecting both ranges. Managed rescheduling keeps the original organizer and selected co-host snapshot. The recipient receives one unguessable management capability whose hash is stored; caller idempotency, provider transaction identity, and calendar-account ownership remain separate fields.
6. The worker creates the provider event, includes active co-hosts, the primary recipient, and up to five deduplicated additional guests, and captures the generated Google Meet or Teams URL. Native-conference creation withholds every attendee until the join URL exists, then verifies the full attendee list in a provider update. Zoom meeting types attach their configured room URL.
7. Calendar success queues SMTP-backed confirmation and reminder jobs. Reschedule and cancellation requests keep the original rep, update or remove the provider event, replace the reminder, and send the matching lifecycle notice.

## Operator handoff path

1. An operator chooses a published Smart Router Link and enters the prospect details using that link's current qualification fields; the old ownership-only API tester remains separate.
2. Qualification resolves any connected HubSpot contact owner through the same server-side path as direct routing, then creates the same short-lived, hashed routing session as the public Smart Router without consuming an assignment. The operator can see the matched rule, pool, and meeting type, while no representative is selected yet.
3. Hot Potato combines the eligible pool's future working hours with every selected Google and Outlook conflict calendar, then subtracts the current booking ledger even when provider results came from the short cache, and shows the resulting slots in the operator's timezone.
4. Selecting a slot first acquires a short durable attempt lease on the qualification session, including the exact UTC range. Concurrent calls and reload recovery see that authoritative in-flight range and cannot perform duplicate provider reads. The lease owner then performs the live recheck and may commit the one atomic Smart Router booking transaction; a stale owner cannot commit after a replacement lease takes over.
5. The durable booking ledger owns assignment, CRM writeback, calendar creation, conferencing, invitation, confirmation, reminder, and the recipient management link. Its availability quote records the exact rep, provider, account, and conflict-calendar set used for the final check. A failed provider create keeps its exact rep/time range reserved because a timed-out provider may still have created the event. Retry or close then looks up the booking's deterministic transaction on that same account: retry may reuse a strictly validated event or fresh-check an absent exact slot; close removes a found event and releases an absent one only after a quiet period plus two separated negative checks. Provider errors always stay locked. Normal scheduling-link creates enter the same read-only reconciliation automatically after their write retries are exhausted.
6. The operator tab keeps only the opaque session token, stable Smart Link ID, chosen time, and public match labels in session storage—never attendee identity or answers. Reload recovery checks booking or active-attempt status first, falls back to the still-valid unbooked session only after the server attests that neither exists, and follows a renamed or unpublished link by stable ID; an unresolved assigned booking cannot be replaced by a new qualification.
7. Historical jobs are audit and delivery records, never slot locks. The migration converts pre-ledger dashboard and public calendar jobs before retiring their old exact-slot index. Active booking time ranges are then the single concurrency boundary for public links, Smart Router Links, operator handoffs, cancellation, and rescheduling. A pending or terminally uncertain reschedule reserves both its original provider-event range and requested replacement; retry can requeue only that exact change. Legacy attendee invitation intent is recorded explicitly so an old no-invite booking never starts sending lifecycle email merely because it was upgraded. Reconciliation still records a provider event found for an already-ended meeting, but it never sends a stale confirmation or reminder.

## Operator identity path

1. Bootstrap creates one named owner from the self-hosted environment and stores only a scrypt password hash. Normal restarts preserve in-app password, role, and active-status changes; the explicit one-run recovery flag restores the configured owner role and access, resets the password when needed, and revokes that owner's sessions. The reference Compose deployment passes the recovery password only to bootstrap; web runtime code never reads it.
2. Login is same-origin JSON, body-limited, and rate-limited by both account and trusted client address. A successful login creates a random `hp_session_…` capability whose SHA-256 hash, organization membership, expiry, last use, and revocation state live in PostgreSQL.
3. The browser receives only an HTTP-only, `SameSite=Lax` cookie, marked `Secure` on HTTPS. Protected APIs return JSON errors while workspace navigation redirects to login; signed provider callbacks remain public.
4. Owners and admins can manage workspace settings, reusable schedules, every representative calendar, and Outlook access keys. Operators can run Handoff, direct routing, and reporting, and can manage only the calendar, weekly schedule assignment, timezone, date overrides, and daily/weekly meeting limits of the exact active representative matched to their login. Reusable-schedule, Outlook key, OAuth, calendar, and working-hours routes repeat their scoped authorization inside the handler or repository transaction.
5. Owners and admins issue random `hp_access_…` invitation and password-reset links. Only the SHA-256 hash, purpose, target, expiry, use, and revocation state are retained. Consumption is one transaction: an invitation creates the active membership while a reset replaces the password, and either path revokes earlier sessions before creating the new browser session.
6. People & Access enforces its role policy in the repository: only owners manage owners, nobody can change their own role or active state, the last active owner is protected, and any role or active-state change revokes that member's sessions. Matching member and representative email exposes Google/Outlook readiness without granting calendar access.
7. Every member can replace their password and list or revoke their own sessions. The current session is preserved during an in-app password change; sign-out revokes that exact database session before clearing the cookie. The old connector setup secret is gone: an authenticated admin session authorizes installation start, while provider state cookies and Microsoft PKCE still bind the callback.

## Existing-form bridge path

1. The operator pins a bridge to one active Smart Router Link configuration, exact allowed website origins, one provider adapter, and an explicit source-field map. A later Smart Link edit makes that bridge unavailable until the mapping is reviewed and republished.
2. The public loader fetches only the router path, provider/form identifiers, origins, and mapping. HubSpot forms made with the updated editor open from its official successful-submission event; legacy HubSpot forms and other systems use the manual API after the host has verified persistence. Neither path intercepts or blocks the source form.
3. The loader selects only mapped values, deduplicates by the provider submission ID, and opens an accessible modal containing the existing sandboxed Smart Router iframe. Identity and answers travel once in a validated, origin-bound `postMessage`; they never appear in the iframe URL, DOM marker, browser event, or public config.
4. The iframe route re-resolves the active bridge ID and enables bridge mode only when its exact Smart Link path and parent origin still match. The iframe then validates the parent window, exact origin, protocol version, bounded message shape, and exact current question set before qualification. Normal public rate limits, short-lived hashed sessions, live calendar checks, and booking-time rechecks still apply.
5. Missing config, stale mapping, disallowed origin, invalid data, provider redirect, or iframe failure leaves the source form's original success state intact. A verified submission retries transient config and pre-ready iframe failures; duplicate callbacks stay suppressed after the iframe accepts the handoff. Closing an accepted scheduler suspends the same iframe and exposes a PII-free resume control, so the live session can finish without replaying the source submission.

## Email compose path

1. Gmail invokes one Google Workspace HTTP add-on endpoint with a Google-signed system ID token and a signed end-user ID token. The server verifies both exact audiences, issuer, service-account email, verified user email, and token expiry before resolving that email to exactly one active representative.
2. Outlook normally requests Hot Potato's delegated `access_as_user` scope through Microsoft Entra NAA. The API validates the access token's signature, version, audience, issuer, tenant, authorized client, scope, and expiry, then resolves its stable tenant-and-subject pair through a durable representative binding. The first connection must also present one active rep-scoped `hp_email_…` fallback key; PostgreSQL binds that key, Microsoft principal, organization, and representative atomically. Unsupported clients may use the same key directly.
3. The repository returns a deliberately small catalog: active meeting types available to that rep and active organization Smart Router Links. It does not return rep email, routing rules, qualification questions, decisions, calendar providers, or OAuth state.
4. `packages/email-composer` formats safe HTML/plain text, presents up to twelve localized choices, preselects three across different local days when possible, and accepts one to five distinct selections. Smart Router Links are link-only because the destination is unknown until the recipient qualifies.
5. The picker uses the same mixed-calendar public availability path as the booking page. Before insertion, the server refreshes availability and requires every selected UTC start to remain present; a stale selection inserts nothing and returns current alternatives. Resulting URLs carry only a UTC `time` hint—never recipient data and never a reservation.
6. Gmail returns the official `updateDraftActionMarkup` host-app action and requests all manifest scopes again when Google's granular-consent event shows a partial grant. Outlook loads Office.js in a route-specific document head, uses `getTypeAsync` plus `setSelectedDataAsync`, and falls back to plain text when HTML insertion fails. Both clients lock duplicate insertion while work is in flight; neither reads or sends the draft, subject, recipients, or attachments.
7. The scheduling page accepts a hint only when it appears in freshly loaded availability. A stale hint produces an explanation and current alternatives; booking remains a separate, explicit, rate-limited POST with a final live recheck.

External IDs are protected by their own transaction lock. Retried form submissions return the original decision rather than advancing the pool again.

## Boundaries

- `packages/router` has no database or framework dependency. Rules, selection, and timezone-aware slot generation can be tested deterministically.
- `packages/email-composer` is browser-safe and owns only deterministic selection, safe email markup, and the versioned insertion message contract.
- `packages/db` owns persistence and transactional coordination.
- `apps/web` owns validation, OAuth callbacks, calendar free/busy checks, the HTTP surface, and operator experience.
- `apps/worker` owns asynchronous side effects, including HubSpot contact-owner writeback, Google/Outlook event lifecycle operations, and email delivery.
- `packages/integrations` owns encrypted token handling, refresh, and provider HTTP adapters.

## OAuth storage

Access and refresh tokens are encrypted with AES-256-GCM before PostgreSQL storage. Organization connectors and rep-owned calendar connectors are stored separately; rep tokens are keyed to exactly one representative. The encryption key stays in the runtime environment. Installation starts require an owner or admin session; provider callbacks still require exact state and PKCE where supported.

Refresh writes use compare-and-swap guards over the exact external account and encrypted refresh-token generation, so a late refresh cannot overwrite a reconnect. A known account cannot be replaced while it owns future or unresolved bookings. Legacy bookings with no account identity cannot mutate a provider until an operator proves the exact account, transaction/event, and time range; a missing stored connection identity may reconnect only to establish that proof boundary.

Outlook compose identity is separate from calendar OAuth. Its NAA app exposes only Hot Potato's own `access_as_user` delegated scope; it does not grant Graph or mailbox access. Authorization uses the token's stable tenant-and-subject pair rather than a mutable email claim. Fallback pairing-key raw values are shown once and retained only in the task-pane WebView's session storage, never Office roaming settings; the database holds a SHA-256 hash plus organization, rep, client, use, and revocation metadata. The Microsoft binding depends on its bootstrap key remaining active, so one admin revocation disables both paths. Only an owner or admin session can list, create, or revoke those keys. Gmail separately uses verified Google identity. None of these compose identities is reused as calendar authorization.

## Deployment

The required infrastructure is PostgreSQL. Web and worker processes can run together on a small host or scale independently. The reference Compose file is deliberately cloud-neutral and binds published ports to loopback by default. Its bootstrap creates only the configured organization and named owner when missing; it can reset that owner's password without reseeding workspace data. The bootstrap container alone receives the recovery password. The sample Acme data is an explicit demo profile rather than a restart dependency. Provider credentials and OAuth callback origins are environment configuration, never seed data, and every provider used for asynchronous writes must be configured in the worker as well as the web process. Native Gmail and Outlook integrations require one stable public HTTPS origin; their checked-in deployment templates remain separate from runtime secrets and environment-specific rendered manifests. Client-IP headers are ignored unless one trusted proxy header is explicitly configured, while a non-spoofable per-link booking ceiling remains active. Pool availability uses a shared 20-second deadline and stops launching calendar checks after it expires so compose requests cannot hang behind a large degraded pool. Each claimed background job receives a unique database lease token; only that exact claim may complete or fail it. Calendar operations receive a real abort signal with a deadline below the reclaim window, preventing a stale worker from changing provider or booking state after a successor takes ownership.
